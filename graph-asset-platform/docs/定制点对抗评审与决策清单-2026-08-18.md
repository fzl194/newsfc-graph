# 平台「上传产品文档」定制点对抗评审与决策清单

> **状态：待专家拍板**（2026-08-18）。本文档只陈述现状/风险/备选/建议，**未改任何代码**；
> 每个决策点等你逐项裁定后，批准的项才进入修复实现。
> 审查方式：3 个独立对抗审查 Agent（构建编排 / 后端安全并发 / 前端数据一致性）+ 实测抽样。
> 范围：本次新增的平台定制代码（runner / productdoc / jobs / docs / fs-raw / 前端）；
> 构建脚本拷贝件（exporter / command / feature）与规范侧字节一致，**未审查修改建议，不在决策范围**。

## 一、CRITICAL —— 阻塞使用或安全底线（5 项，建议优先裁定）

### D1. nf/version 表单未校验 → 路径穿越可删任意目录
- **现状**：`productdoc.py` 对 `nf`/`version` 只做非空 strip，随后拼入 `output/{nf}_{version}`（rmtree）和 force 时 `assets/{层}/{nf}/{version}`（rmtree）。
- **风险**：`nf="../../Users/xxx"` 即可让 rmtree 逃逸到数据目录之外（需 upload+assets 权限，但这是核心权限组）。**本次审查最大安全洞**。
- **备选**：a) 入口白名单正则 `^[A-Za-z0-9_-]{1,32}$`；b) runner 内 resolve 后校验祖先目录（纵深防御）。
- **建议**：a+b 双层。
- **待拍板**：是否认可白名单字符集？version 是否允许 `.`（如 20.15.2——**必须允许**，正则需含点）？

### D2. 图片请求带不了鉴权头 → 全部图片仍会裂（功能级断裂）
- **现状**：前端鉴权走 `X-API-Key` 请求头；`<img src="/api/v1/fs/raw?...">` 由浏览器发起，**无法携带自定义头** → AuthMiddleware 401。
- **风险**：图片渲染链路（URL 重写 + raw 端点）在真实登录态下**整体不可用**——比 D3 更根本。
- **备选**：a) raw 端点支持 `?key=` 查询参数（与现有 KEY 体系一致）；b) raw 端点免鉴权（内网放行）；c) 前端 fetch blob + objectURL（内存代价大，不推荐）。
- **建议**：a（URL 里带 key，仅限 raw 端点；注意 key 入 URL 的日志泄露面——内网可接受需你确认）。
- **待拍板**：a / b / c？若 a，key 出现在访问日志中是否可接受？

### D3. 图片 URL 空格断裂：实测 258+ 处真实引用不匹配
- **现状**：前端 `resolveImgUrls` 正则 `\(([^)\s]+)\)` 排除含空格 URL。实测三层图谱资产抽样：**≥258 处 / ≥250 文件**的图片引用路径含空格与中文括号（如 `![](设置升级观察期(SET UPGRADEWATCH)_13530392.assets/notice_3.0-zh-cn.png)`），全部不会被重写 → 裂图；且路径内 `)` 使正则截断，放宽 `\s` 也无效。`<img>` 标签与 `#fragment` 实测 **0 处**，无此风险。
- **风险**：相当比例命令/配置对象文档的插图无法显示。
- **备选**：a) 前端正则放宽 + 中文括号配对修正（复杂正则，脆）；b) **构建管线规范化**：图片拷贝时文件名净化（去空格/中文括号）——需改规范侧 `rewrite_images`（升版本走 CR，不属于平台擅改）；c) 后端渲染前统一改写（对象接口返回 body 前做一次服务端重写）。
- **建议**：c（平台侧解决，不动规范脚本：`/objects` 返回 body_md 前按 source_path 重写图片引用，空格路径用 encodeURIComponent 处理即可，无正则匹配问题——服务端知道确切目录，可用更稳的解析）；长期 b 作为规范演进提议。
- **待拍板**：选 a/b/c？（b 需要走规范 CR 流程）

### D4. 上传 277MB~856MB 全量读内存 + 无大小上限
- **现状**：`await file.read()` 一次性读入内存再落盘；无文件大小限制。
- **风险**：内存峰值大对象常驻（CPython 不还 OS）；并发两个上传叠加；误传超大文件直接打爆。
- **备选**：a) 分块流式写（8MB chunk 循环）；b) 加显式上限（如 2GB，超限 413）。
- **建议**：a+b，改动约 10 行。
- **待拍板**：上限值定多少？（真实 hwics 实测 277MB，建议 2GB）

### D5. force 覆盖重建会**静默剥掉 Command 层正文里的特性引用**
- **现状**：force 先 rmtree `Feature/{nf}/{version}` 再跑 `build_commands`；而 build_commands 的特性引用解析 `feature_codes` **读的是已落盘的 Feature 资产目录**（规范脚本固有逻辑，增量场景没问题）→ force 场景目录已空 → 命令 md 里所有 `[[nf@Feature@…]]` 引用被剥成纯文字，且不报错（规范定义的静默降级）。
- **风险**：每次"覆盖重建"系统性丢失命令→特性跳转；这是**平台编排顺序与规范脚本依赖的冲突**，不是脚本 bug。
- **备选**：a) 构建两遍：commands→configobjects→licenses→features 后**再跑一遍 commands+configobjects**（幂等，第二遍 feature_codes 齐全）；b) force 时不删 Feature，构建完后清理孤儿文件；c) 仅在 manifest `refs_stripped` 超阈值时打警告（不修复只提示）。
- **建议**：a（第二遍只补引用，成本一次构建时间）；c 顺手加。
- **待拍板**：选 a/b/c？

## 二、HIGH —— 正确性与体验（8 项）

### D6. 互斥检查存在竞态窗口（TOCTOU）
- **现状**：`has_processing` 检查与 `create_job` 之间隔着 4 次目录扫描 + 277MB 读盘，窗口秒级；两个并发 POST 可都通过 → 两个构建并发 rmtree/写同目录。
- **备选**：a) 模块级线程锁包住 检查→建任务；b) import_jobs 表加部分唯一索引（`WHERE status='processing'`）DB 兜底。
- **建议**：a（单 worker 部署足够）+ b（防未来多 worker）。
- **待拍板**：是否同时上 a+b？平台是否会用多 worker 部署？

### D7. jobs 后台线程无锁写共享 SQLite 连接
- **现状**：runner 线程每步 `_persist` 直接写 `get_shared_db()` 共享连接（`check_same_thread=False` 只关检查不改线程安全性），与 telemetry/fs 写并发；持久化失败 `except: pass` 静默吞。
- **风险**：跨线程同时 execute 同一连接是未定义行为；锁外 commit 可能截断 fs 写事务。
- **备选**：a) jobs 全部操作纳入 import_lock；b) jobs 用**独立 SQLite 连接**（WAL 支持多连接）+ busy_timeout；c) 至少给 _persist 失败加日志。
- **建议**：b + c（最干净，不动现有锁语义）；另 sweep 与 mtime 线程的并发同根消失。
- **待拍板**：a/b？

### D8. docs 根右键菜单泄漏写操作入口（实测可复现）
- **现状**：`FsBrowserView.menuItems` 只看 `canAssets` 不看数据源——「原始产品文档」模式右键仍出现 重命名/移动/删除/上传，点击会把 **docs 树的 path 传给 assets 树的写 API**（轻则 404，路径同形时可能误操作资产库）。
- **建议**：menuItems 顶部按 source 短路（docs 模式只留"打开"）。一行守卫。
- **待拍板**：确认修法即可（这属明确 bug，不涉设计取舍）。

### D9. svg 在图片白名单内 → 存储型 XSS 面
- **现状**：`/fs/raw`、`/docs/raw` 白名单含 `.svg`，FileResponse 以 `image/svg+xml` 同源直发（可嵌 script）。
- **风险**：能接触 assets 目录的人放入恶意 svg → 同源脚本执行（内部平台、写入面受限，定 HIGH）。
- **备选**：a) 白名单剔除 svg；b) 保留但响应头加 `Content-Security-Policy: sandbox`。
- **建议**：a（svg 在 md 引用场景罕见）。
- **待拍板**：a/b？业务上有 svg 插图需求吗？

### D10. 旧 output 导出在解压**之前**被删 → 失败即"资产在、原文没了"
- **现状**：`runner` 一进来就 rmtree `output/{nf}_{version}`，解压/转换失败时旧 md 已不可逆销毁（不进回收站）。
- **备选**：a) 先导出到 `output/.tmp_…`，**成功后**原子替换，旧目录移入 `.trash`；b) 仅把旧目录先 move 进 .trash 再解压。
- **建议**：a。
- **待拍板**：a/b？旧导出要不要进回收站（还是直接删）？

### D11. 源目录定位的三个子问题（你点名的路径识别）
- **现状**：① 严格匹配（目录名含 nf+关键词）命中**多个**时静默取排序第一个、无警告；② 关键词表封闭（`MML命令`/`特性指南`/`License描述` 三个），无变体（`MML 命令`带空格、`命令参考`、`License 控制`、英文目录）；③ nf 匹配大小写敏感（填 `udg` 严格匹配全灭）。
- **风险**：①双语/废弃目录共存时可能选错且无感知；②真实归档目录名变体会直接定位失败；③大小写陷阱。另：归档缺 License 卷时，泛匹配唯一候选可能错定位到 `License控制原理` 这类非控制项目录。
- **备选**：①多候选也降级 warning + 启发式取"路径最浅/名最短"；②每类关键词扩为变体集合；③nf 匹配 casefold；④泛匹配对 license 类加排除词（`原理|介绍|概念`）。
- **建议**：①②③都做；④可选。**需要你提供真实归档的目录名变体样本**（不同产品线的产品文档，MML 命令/特性指南/License 目录都叫什么）——这是专家经验的关键输入。
- **待拍板**：变体清单 + 是否要"多候选时报错让人工选"的严格模式？

### D12. 大文件上传零反馈（无进度/无取消/无超时）
- **现状**：fetch + FormData 直传，277MB 上传期间按钮显示"构建中…"（实为上传中），用户无法区分阶段。
- **备选**：a) 改 XHR 用 `upload.onprogress` 真实进度条 + 阶段区分（上传 xx% → 解析 → 构建）；b) 分块/断点续传（需后端配套，成本高）。
- **建议**：a 本次做；b 列路线图不做。
- **待拍板**：a 够吗？内网上传带宽大概多少（决定进度条必要性）？

### D13. 轮询无限重试 → 后端重启后前端永久卡"构建中"
- **现状**：`pollJob` catch 无限吞错重试；job 记录 404 后每 2s 打一次直到关页，提交按钮永久禁用。
- **备选**：连续 5 次失败即停 + 提示"任务状态未知，请刷新"；404 单独判死。
- **建议**：两者都加，几行代码。
- **待拍板**：确认策略（阈值 5 次可否）。

## 三、MEDIUM —— 需要决策但可排期（8 项）

### D14. 版本不一致只警告不阻断
- **现状**：导出根目录名不含用户填的 version → 仅 warning。用户填错 version 会产出**全新 version 目录**的资产，与真实版本永久分裂，事后纠正成本高（force 清理+重传）。
- **备选**：a) 从目录名正则抽版本号，抽取成功且与表单不一致 → **阻断并返回抽取值供确认**；抽不到才降级 warning；b) 维持现状。
- **建议**：a（"可确认的阻断"）。
- **待拍板**：a/b？

### D15. /docs*（原始产品文档）权限定级
- **现状**：默认 frontend 权限（任何登录用户可浏览全部原始产品文档）；与 /fs*（assets 权限）不对称。
- **建议**：业务定级问题——产品文档在你们内部算"登录即可看"还是"资产权限才可看"？前者维持，后者提升到 assets。
- **待拍板**：定级。

### D16. kill 后端后：孤儿子进程可能继续写资产 + `.pdoc_` 临时目录残留
- **现状**：杀进程时 subprocess 起的构建脚本不随父进程终止（无进程组绑定）；下次启动 sweep 把 job 标 failed 后，用户立即重传会与**孤儿进程并发写同一资产目录**。硬 kill 也会留下 GB 级 `.pdoc_`/`.pdoc_up_` 孤儿目录，无启动清扫。
- **备选**：a) runner 记子进程 PID，sweep 时按 PID 树终止；b) 启动时清扫 `.pdoc_*`/`.pdoc_up_*`；c) 构建期间置全局只读标志（防用户同时手改资产）。
- **建议**：a+b 必做；c 可选。
- **待拍板**：a+b 是否纳入？c 要不要？

### D17. 上传 zip 的 Zip Slip 预检
- **现状**：exporter `extractall` 直接解压用户上传归档，无成员路径校验（exporter 是权威拷贝不能改，但**编排层选择了直接喂上传物**）。
- **备选**：runner 在调 exporter 前做 namelist 预检（拒绝绝对路径/`..`/符号链接成员）——不动 exporter。
- **建议**：加（内网单用户风险低，但作为平台安全底线值得）。
- **待拍板**：加否？

### D18. job 错误堆栈直接回显 + 任务无属主
- **现状**：失败时 error 含 3000 字符 traceback（泄露服务端绝对路径）；GET /import/jobs 任何 upload 用户可看全部人的任务。
- **建议**：内网可接受则维持；要收紧则堆栈截断/脱敏 + job 加 owner 字段过滤。
- **待拍板**：维持 or 收紧？

### D19. 历史任务列表上限
- **现状**：后端默认返回 100 条，无分页；超出的旧任务不可见不可删。
- **建议**：放大 limit（500）+ 后端确认上限，真分页列路线图。
- **待拍板**：预期任务量级多大（每天几次？决定要不要真分页）。

### D20. 完成摘要 added 指标失真 + manifest 缺失静默 '?'
- **现状**：`added` 只算命令层数量；manifest 读不到时计数显示 '?' 且不告警（manifest 缺失本身是异常信号）。
- **建议**：added=四层之和；manifest 缺失追加 warning。几行代码。
- **待拍板**：确认即可（无设计取舍）。

### D21. MdPreview source_path 缺失时图片按根目录解析
- **建议**：dir 为空时跳过重写（宁可不显示也不裂错图）。
- **待拍板**：确认即可。

### D22. 两个小体验项
- a) 提交成功后首查失败 → 不启动轮询，UI 无感知（需区分"提交失败"与"首查失败"）；
- b) `FsFileDetail` markdownIt `html:false` 而 MdPreview `html:true`——命令文档表格 `<br>` 在文件详情页显示原文标签，两处渲染不一致（建议统一 html:true + DOMPurify，MdPreview 已有先例）。
- **待拍板**：b 是否统一为 html:true？
