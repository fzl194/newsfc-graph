## 0. 需求复述（请确认理解无误）

1. **中间态全保留**：上传的 .hdx/.hwics 原件、解压后的 html、转换后的 md 三层全部留存——支持未来追溯与免重做（换挖掘脚本重挖时不用重新上传/解压/转换）。〔推翻此前"html 删除"的决策〕

## 1. 目标架构

```
┌─ 步骤① 解压（上传页）────────────────────────────┐
│ .hdx + nf + version ──► 解压 html ──► 转 md      │
│ 产出：一个「产品文档包」（bundle），三层全留存      │
└──────────────────────────────────────────────────┘
                     ↓ （包注册表，可追溯、可复用）
┌─ 步骤② 挖掘（自动抽取页签）──────────────────────┐
│ 选包 → 定位（自动推荐+候选下拉人工确认）           │
│      → 范围勾选 → 模式选择 → 确认 → 后台 job      │
│ 模式=可插拔解析器（注册表驱动）                    │
└──────────────────────────────────────────────────┘
```

### 1.1 产品文档包（bundle）存储布局提案

```
platform-data/output/
  {nf}_{version}/                 ← 一包一目录（沿用现名，见开放问题 Q2）
    source.hwics                  ← 上传原件（277MB+）
    extracted/                    ← 解压 html 全量（GB 级）
    md/                           ← 转换后 md 树（现 output 的内容迁入此层）
    bundle.json                   ← 包元信息：上传人/时间/原文件名/sha256/
                                    exporter 版本/状态/各层大小统计
```

- **md 迁入子目录**的理由：与 html/原件分层清晰；「原始产品文档」浏览默认只挂 `md/` 子树（html 海洋不进浏览树，见开放问题 Q5）。
- **自描述优于建表**：包列表 = 扫描 `output/*/bundle.json`，不新增 DB 表（包本质是文件系统的东西，扫描毫秒级）。旧包（无 bundle.json、无 md/ 层级）识别为"旧格式（仅 md）"，仍可挖掘——挖掘只依赖 md。
- **追溯性**：bundle.json 记录链路（原件哈希→exporter 版本→转换时间），配合已持久化的 mine job 历史，"这批资产从哪个包、哪个脚本版本挖出来的"全程可查。

### 1.2 可插拔解析器（模式）设计提案

```
backend/app/pipeline/modes/
  __init__.py        ← 注册表：MODES = {"5gc": ModeDef, ...}
  fivegc.py          ← 当前模式
```

一个模式定义四件事（全部声明式，新脚本=新文件+注册一行）：

```python
ModeDef(
    id="5gc", name="5GC产品文档",
    keywords={                       # 目录定位关键词（吸收评审清单 D11 的变体表）
        "mml": ["MML命令", "MML 命令", "命令参考"],
        "feature": ["特性指南"],
        "license": ["License描述", "License 控制"],
    },
    builders=[                       # 构建器序列 + 依赖声明
        Builder(cmd="command/build_commands.py", layer="Command", needs=[]),
        Builder(cmd="command/build_configobjects.py", layer="ConfigObject", needs=["Command"]),
        Builder(cmd="feature/build_licenses.py", layer="License", needs=[]),
        Builder(cmd="feature/build_features.py", layer="Feature", needs=["Command", "License"]),
    ],
)
```

- **前端模式下拉 = 注册表枚举**（GET /import/modes），你新增 IMS 模式文件后下拉自动出现——满足"新增解析脚本命名后自动替换"。
- **范围勾选 × 依赖联动**：`needs` 声明使后端能校验勾选合法性（见开放问题 Q4）。
- 未来 IMS/信令模式可能连构建脚本都不同（新建 `pipeline/ims/` 脚本目录，同样拷贝自规范或新规范层）——注册表天然容纳。

### 1.3 交互流（自动抽取页签）关键改进：定位从"自动判定"降级为"默认建议+人工确认"

- 选包后调 `GET /import/bundles/{id}/locate` → 返回三类目录的**自动推荐 + 全部候选清单**（服务端扫描）
- 前端三组下拉：默认选中推荐项，用户可从候选清单改选——**用户只能从服务端枚举的候选里选，不能手输路径**
- 这一设计把评审清单 **D11（定位准确性）从"必须猜对"降级为"建议+确认"**，同时把 **D1（路径穿越）的 mml/feature/license 注入面彻底消除**（nf/version 白名单仍需要）
- 专家经验（目录命名变体）仍有价值——决定默认推荐命中率，但选错不再致命

## 4. 需要你拍板的开放问题（7 个）

**Q1. 磁盘账**：全保留后每包约 3-4GB（原件 277MB+ / html 解压后约 1-2GB / md 数百 MB），多产品线多版本累积可达几十 GB。
   - a) 全接受（磁盘充足）；
   - b) 接受但提供**手动清理**能力（包列表里可单独删 html 层/原件层，保留 md 保证可重挖）；
   - 建议 b——追溯核心是 md（重挖只依赖 md），原件/html 是"深度追溯"层，可按磁盘情况取舍。

**Q2. 同 nf+version 重复上传**：
   - a) 覆盖（一包一目录，旧包整体替换，配合 D10 原子替换）；
   - b) 保留历史（目录加时间戳 `{nf}_{version}_{yyyyMMddHHmm}`，包列表全展示，挖掘任选）；
   - 建议 a（与资产"同 nf+version 唯一"的模型对齐；真要留历史走 b 再说）。

**Q3. 「自动抽取」新页签的权限位**：你说权限粒度=页签级别。新页签：
   - a) 新增独立权限位（如 can_mine），用户管理页同步加勾选；
   - b) 挂在 assets（能看资产库才能挖）；
   - c) 挂在 upload（延续上传流）；
   - 按"页签=权限位"的一致性应选 a；但抽取写资产库，**实施时无论选哪个都会二次校验 assets 写权限**（与产品文档上传相同的纵深防御）。

**Q4. 抽取范围 × 依赖联动**：勾了"特性"但该 nf+version 的 Command/License 资产不存在（且本次不勾）时：
   - a) 前端自动把依赖范围勾上（不可取消，提示依赖关系）；
   - b) 警告放行（接受使用命令边/所需License 边缺失，产出降级资产）；
   - 建议 a（自动补齐），b 作为"高级覆盖"？简化起见先 a。

**Q5. html 在「原始产品文档」浏览树中**：默认只展示 `md/` 子树（html 海洋无浏览价值还拖慢列表）？还是全部可见？建议只展示 md + 顶部一行包元信息（原件名/大小/上传人）。〔权限已按 D15 提升 assets〕

**Q6. 模式命名确认**：当前模式显示名就叫 **"5GC产品文档"**？（UDG/UNC 两个网元共用同一模式，模式与网元正交——同一模式能挖任何 5GC 网元的包。）未来 IMS/信令各注册一个显示名。

**Q7. 两类 job 的互斥关系**：
   - a) 全局单任务（解压或挖掘任一在跑，两类都不能提交）——最保守；
   - b) 各自单任务（一个解压 + 一个挖掘可并行；但挖掘写 assets、解压写 output，无目录冲突，理论安全；唯一交叉是同时首次上传+挖掘同包不可能——挖掘依赖已解压包）；
   - 建议 b（流水线并行更实用：上传解压下一个包的同时挖掘上一个）。
