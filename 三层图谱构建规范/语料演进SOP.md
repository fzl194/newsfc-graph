# 语料演进 SOP（基于任意新语料自适应演进图谱）

> 体裁：**Procedure**——Agent 理解每批语料的实际结构后，**自己构建适合本批的策略与校验**，不是套固定流水线。
> 与 [`演进机制.md`](演进机制.md) 并列：后者管"规范怎么变"（版本/CR/CHANGELOG，治理层）；本 SOP 管"**图谱内容怎么随新语料长**"（Feature/Task/Business 三层的内容演进）。
> 起源：冷启动只靠固定产品文档输入（特性指南），缺激活/配置/方案等更丰富语料（业务专题/配置指导书）；用户后续会持续提供各类新语料（配置指导书转 md，**格式不统一**）。本 SOP 让 Agent 能基于任意新语料**自适应地**补全/修正/演进图谱，而非每次重跑冷启动。

---

## 1. 定位

- **输入**：任意新语料——业务专题、配置指导书、方案文档、运维手册、客户定制文档……转成 md 即可，**格式不预设、不强求结构一致**。
- **输出**：对 Feature 层（簇子文档）、Task 层（FeatureTask/CompoundTask/AtomTask）、Business 层（ConfigurationSolution/NetworkScenario）做**增量**补全/修正/演进，并留痕。
- **不是**：固定 7 步流水线、绑死某语料结构的模板、一刀切脚本。**新语料形态多变，固定流程会失效**——故本 SOP 是"框架 + 工具箱 + 不变量"，Agent 据每批语料实况组合。

---

## 2. 恒定原则（所有语料、所有策略都守，不可裁剪）

1. **跨层根因定位**：症状层 ≠ 根因层。例：Task 层 FT 引用的"激活 §表"在 Feature 簇里找不到，根因常是 **Feature 簇不全**（激活文档漏收），不是 FT 错。**必须定位到根因层再修**，不只在症状层打补丁。常见症状→根因映射：
   - FT 引用找不到 → Feature 簇不全 / atom 未建
   - CS 编排的 FeatureTask 不存在 → Task 层缺建（CS 前置门）
   - 命令在语料里但图谱无 atom → atom 层缺口（先确认是配置类命令）
2. **闭包与可追溯**：每条命令/参数/场景须可回溯到语料来源（文件+段）；Task 层走 [`task/check.md`](task/check.md) B4 信息源边界。
3. **不臆造**：语料无证据则标"待补/待确认"，绝不编命令/参数/场景/特性码。推断（非语料明示）必须显式标注。
4. **冲突调和**：新语料 vs 已有资产冲突——脚本优先于叙述（Task §5.4）、冲突标注不写"通过"（Task §5.5）；保留 Feature 实际语义。
5. **可复现性纪律**：手工回填/修正 = 必须提 CR + 资产内 stopgap 注 + CHANGELOG 留痕，声明"待自动化重建"；**不破坏构建器可复现性而不留痕**。正解是扩构建器输入（见各层 CR），手工是过渡。

---

## 3. 自适应主流程（Agent 按本批语料实况走，产出可审计的策略单+校验单）

### Phase 0 · 语料辨识（必做，所有语料）

抽样读语料（首/中/尾各取若干），刻画**语料画像**：

- **含什么**：业务场景？配置步骤？命令（MML）？参数表？原理叙述？组网/流程图？调测操作？
- **怎么引用图谱实体**（映射信号可用性，关键）：
  - 有 `特性映射.md` / 特性码表（`GWFD-xxxxxx`）？
  - 正文/标题含特性码？
  - 含 License 项（`LKVxxx`）？
  - 命令以粗体/链接/脚本行形式出现（`**CMD**` / `[**CMD**](url)` / `CMD:..;`）？
  - 还是纯叙述、无任何显式引用？
- **格式特征**：标题层级、表格结构、脚本块形态、章节组织、图片。
- **输出**：语料画像 = 一句话结构总结 + 可用映射信号清单 + 不确定点。

### Phase 1 · 策略构建（Agent 据画像定制，**不套固定模板**）

基于画像决定，输出**本批策略单**（可审计、可复查）：

- **触哪些层**（按语料内容定，非全打）：Feature 簇回填子文档？Task 层 FeatureTask 演进/修正？Business 层 CS 新建或更新？atom 补建？
- **映射规则**（把语料映射到图谱实体）——按信号可用性**优先级**选：
  1. 特性映射表（最可靠，语料自带）
  2. 特性码正则（`[A-Z]{2,5}FD-\d{6}`）
  3. License 项（`LKVxxx` → 反查 License 资产所属特性）
  4. 命令指纹（命中的 atom/CT → 反推所属 FeatureTask/特性）
  5. 场景语义反推（最弱，需人工确认）
  - 映射到**多特性**时：入 Business 层 CS 的"特性关系矩阵"归属（核心/基础依赖/维度增强/跨网元对端/二选一，见 [`business/SKILL.md`](business/SKILL.md)）。
- **回填动作清单**：哪些簇/FT/CS/atom 要新建或改，各依据语料哪一段（文件+段）。
- **风险与不确定点**：哪些映射是推断（非语料明示），需标注"待确认"。

### Phase 2 · 执行

按策略单回填/修正/建新；**每个变更标注语料来源**（文件+段）；推断项标"待确认"；不臆造。

### Phase 3 · 个性化校验（Agent 据本批策略单**自行设计**校验项——用户明确要求）

针对本批策略**自己定校验项**（不是跑固定 checklist），再叠加恒定不变量。

**据策略类型选校验项（示例，非穷举）**：
- 策略=配置指导书→CS：校验"每场景命令序列完整进 CS 编排"+"CS 编排的 FeatureTask 都已存在（CS 前置门）"+"抽 N 场景对照源脚本"+"License 项映射到的特性集合自洽"。
- 策略=激活文档→Feature 簇回填：校验"回填子文档 doc_type 正确"+"概述 `## 边` 补包含子文档"+"子文档 `属于特性` 边"+"对应 FT 引子链接新激活子文档"+"FT 命令闭包/参数闭包 0 缺（对照新可用激活文档）"。
- 策略=裸场景反推特性：校验"无臆造特性码"+"未映射命令标待 atom"+"License→特性映射自洽"+"多对一归属进 CS 特性关系矩阵"。

**叠加恒定不变量（必跑）**：闭包（命令/参数/场景）、可追溯（每变更有源）、B4 信息源边界、不臆造、跨层根因（症状层与根因层都核到）。

**输出**：本批校验单 + 结果（CLEAN / 缺陷清单 with 严重级）。

### Phase 4 · 留痕

- CR（含策略单 + 校验单 + 可复现性声明）进对应层 `change-requests/`。
- CHANGELOG append（按 [`演进机制.md`](演进机制.md) 格式）。
- 手工回填的资产内加 stopgap 注（标日期 + 来源 + 待自动化重建 + CR 链接）。

## 4. 工具原语（Agent 按需组合的工具箱，**非固定脚本**）

提供可复用原子，Agent 据策略单组合。未来语料格式不固定，**固定脚本会失效**；其中机械化、跨语料稳定的部分可沉淀为 helper 脚本（交集成），但非本 SOP 强制。

- **语义目录自动发现**：复用 [`task/scripts/collect_command_examples.py`](task/scripts/collect_command_examples.py) 的 `discover_raw_dirs`（按目录名如"业务专题/网络部署/配置指导书"在 `--doc-root` 下 `rglob` 自动定位，跨网元/版本结构差异自适应）。
- **实体抽取正则**：特性码 `[A-Z]{2,5}FD-\d{6}` / License 项 `LKV[0-9A-Z]+` / 命令名（粗体 `[**CMD**](url)` / `**CMD**` / 脚本行首 `CMD:`）。
- **倒排索引骨架**（复用 `build_command_index`）：扫每个文档一次 → `{实体: [文档]}`，避免 O(实体×文档) 暴力扫。
- **特性映射表解析**：解析 `特性映射.md` 这类 `| 功能 | 特性ID | License |` 表 → code/License 映射；**有则用，无则跳**（不强求语料都有）。
- **场景/步骤切分**：按标题层级 / 任务示例脚本块 / "场景一/场景二" 切分场景单元。
- **CS 特性关系矩阵归属**：把匿名步骤反推到的多特性，按角色（核心/基础依赖/维度增强/...）填 CS 矩阵（[`business/SKILL.md`](business/SKILL.md)）。
- **信号判定**（复用 `detect_signals` 思路）：强证据=数据规划表行/任务脚本行；弱信号=纯 prose，不单独命中（防参考信息页污染）。

> Agent 用原语按策略组合。例：裸场景配置指导书 → 用"语义目录发现"定位 → "场景切分"分场景 → "命令抽取+倒排索引"命中文档里的命令 → "命令指纹"反推 atom/CT/FeatureTask → 多对一入"CS 特性关系矩阵"。

## 5. 参考模式（已知两种，**非穷举**；Agent 遇新形态自行扩展）

### 模式 A · 结构化语料（业务专题型）
- 特征：有 `特性映射.md` + 激活文档 + 原理/差异/调测；文档按特性/变体分目录。
- 策略：经特性映射直连 feature_code → Feature 簇回填子文档（激活/原理/约束/参考信息）→ FT 核对修正 + 引子链激活子文档。
- **worked example**：见附录（头增强族 + 防欺诈族，CR-[20260807-002]）。

### 模式 B · 裸场景语料（配置指导书型）
- 特征：只有"业务场景 + 配置步骤 + 命令脚本"，**不点名特性/步骤**，可能跨多特性。
- 策略：命令指纹/License/场景语义**反推**映射到的特性集合 → 多对一入 Business 层 CS（特性关系矩阵归属）→ CS 编排的 FeatureTask 缺则先补建（CS 前置门）→ 未映射命令标"待 atom"。
- 校验重点：无臆造特性码；CS 编排 FeatureTask 全存在；场景命令序列完整进 CS。

### 遇混合 / 新形态
Phase 0 识别 → Phase 1 组合两模式或**自创新策略**（在策略单里写明理由）→ Phase 3 定制校验。**不强制套 A/B**。

## 6. 与现有规范的关系

- [`演进机制.md`](演进机制.md)：规范演进（版本/CR/CHANGELOG/兼容性）——本 SOP 的留痕（Phase 4）走它的回路。
- [`task/scripts/collect_command_examples.py`](task/scripts/collect_command_examples.py)：atom 输入的跨语料扫描先例——本 SOP 工具原语的主要来源。
- [`task/check.md`](task/check.md) B4（信息源边界）+ B1/B2（命令/参数闭包）：本 SOP Phase 3 校验的 Task 层不变量。
- [`business/SKILL.md`](business/SKILL.md) ConfigurationSolution：配置指导书的天然图谱载体（`编排特性→FeatureTask / 复用步骤→CompoundTask / 复用命令→AtomTask` 边 + 特性关系矩阵 + 前置门）。模式 B 的核心落点。
- 各层 `change-requests/`：本 SOP Phase 4 留痕的去处（Feature/Task/Business 各自）。

## 7. 附录：头增强试点（模式 A worked example，2026-08-11）

**语料**：`output/.../特性部署/业务专题/UDG头增强功能专题/` + `UDG防欺诈功能专题/`。

**Phase 0 画像**：结构化业务专题——含 `特性映射.md`（topic→GWFD-110261/262/263 + License）+ 每变体 `激活/原理/约束限制/参考信息/调测`；命令以 `[**CMD**](url)` 粗体链接出现；图片在 `.assets/`。映射信号：特性映射表（强）+ 特性码（强）+ License（强）。不确定点：NSH 头增强在专题里但特性映射未列。

**Phase 1 策略单**：触 Feature 层（簇回填）+ Task 层（FT 核对）。映射规则=特性映射表直连 feature_code（HTTP→110261/RTSP→110262/HTTPS→110263；防欺诈族 110401 在另一专题）。回填清单=4 簇各 激活+原理+约束+参考信息 子文档。风险=NSH 无特性码（标待确认，不盲建）；共享文档"差异"跨簇（本轮不入簇，已在 FT 决策点体现）。

**Phase 2 执行**：4 簇 15 子文档手工回填（frontmatter+stopgap 注+命令引用转 `[[UDG@MMLCommand@...]]`+图片拷 assets/+`属于特性` 边+概述补`包含子文档`）；FT 引子补链激活子文档。详见 [`feature/change-requests/CR-20260807-002`](feature/change-requests/CR-20260807-002-业务专题纳入Feature簇构建.md)。

**Phase 3 校验单**（策略=激活文档→簇回填，故校验）：① 子文档 doc_type 正确 ✓ ② 概述补包含子文档 ✓ ③ 子文档属于特性边 ✓ ④ FT 引子链激活子文档 ✓ ⑤ FT 命令/参数闭包对照激活文档：110261/110262/110401 CLEAN，110263 补 PRIORITY=10 ✓ ⑥ 跨层根因：症状(FT 引用找不到)根因(Feature 簇不全)已修 ✓ ⑦ 不臆造：110401 无参考信息源→跳过未编 ✓

**Phase 4 留痕**：CR-20260807-002（Feature 层）+ 各子文档 stopgap 注 + CHANGELOG 0.18.0 + 本 SOP。可复现声明：手工回填待 `build_features.py` 扩展（加 topic-dir + 特性映射解析）后自动化重建。

**经验沉淀（供下批语料参照"思路"而非"步骤"）**：
- 业务专题是结构化语料的典型——有特性映射就直连，省反推。
- 共享文档（如"差异"）跨簇，不强塞进单一簇；其知识已在 FT 决策点体现即可。
- 簇回填后，FT 引子要补链簇内激活子文档（统一为簇内 wikilink，不再引外部业务专题路径）。
- activation 文档自身可能有内部不一致（如 REFRESHTYPE 表 vs 脚本）——记录，待自动化重建时核，不臆改。
