# CR-20260807-001-Task层信息可追溯性与SOP权威统一

> 状态：✅ 已采纳 / 已落地（v0.17.0，2026-08-07）。落地动作见文末"落地记录"。

## 场景

对**全量 UDG Task 层**（246 FeatureTask + 46 CompoundTask + ~250 AtomTask，跨 4.1/4.2/4.3）做信息丢失审计（分层抽样 ~48 FT + 60 边界声明 FT 定向扫查），发现两类系统性问题：

**A. 信息可追溯性无机制兜底**（用户核心担忧："从特性层知识到 task 层知识没有丢失信息，尤其命令级、参数级"）：
- 当前唯一信息丢失防线是**人工对抗评审**。`audit_compound_feature.py` 的 D5（atom 覆盖）是 info 级不 fail；**没有命令级闭包检查**（Feature 簇脚本命令 ⊆ FT流程+CT场景差异+省略列）；**没有参数级闭包检查**（Feature 数据规划 param=value ⊆ FT/CT 或标注待补/冲突）；**没有反向追溯**（Task→Feature，防"臆造变体行"）。
- 实测抽样 ~108 FT 仅 1 个真缺陷（GWFD-112001：FT 信息源边界声明覆盖概述+业务配置，但簇内 初始配置.md/镜像SIP信令功能.md 承载的 SET NETYPE / ADD VPNINST+SET SIPSIGMIRRORPARA+SET SOFTPARA 既未覆盖也未枚举排除；USERPROFILE/RULEBINDING 可选分支被当必配）——定向扫查 60 个边界声明 FT 确认此为孤例（59 个对账正确），但**根因是 SOP 没有强制信息源边界对账**。

**B. SOP/handoff/template 三方矛盾**（构建方读哪本、审查方按哪本不一致）：
- `SKILL.md §B.2` 列 FT 正文 6 段，**连 `## 参数核对` 都没列**；`template/feature_task.md.tpl` 要求 7 段（含参数核对）；handoff `UDG-4.1-交接.md §5.1-§5.10` 是构建方事实标准（"§5.4 时序/§5.5 参数合法性/§5.7 调测剥离/7 段/GWFD-110201"术语皆出于此），**但不在 SOP 内**。
- `command_set` 成员定义模糊（字段定义说"命令名列表"，实指"本 CT 编排的组成 atom 命令"，不含上游前置）——曾致 010155 C1/C2 缺陷（ADD VPNINST 误入 command_set+上游）。
- atom 范围：SOP §A.2 写"所有命令都建 atom"，但用户决策"非配置类（DSP/LST/EXP/调测）不建"未回写 SOP。
- CT 阈值："<3 distinct atom → 直引不抽 CT"、"相位同义"判定只在 handoff，不在 SOP。

## 建议的规范补丁

### 1. SOP 权威统一（解决三方矛盾）

- **`SKILL.md §B.2` 增 `## 参数核对`**：FT 正文正式定为 **7 段**（引子+配置概览+配置流程+激活方法与参数差异+**参数核对**+决策点+约束+边），与 template 对齐。
- **`SKILL.md` 顶部加"单一权威"声明**：SKILL.md + 字段定义.md + template + check.md 为 Task 层规范唯一权威；handoff/ 为历史交接记录（构建进度/教训），**不作为规范引用源**；handoff §5.x 规则已吸收进 SKILL.md 本版。
- **handoff 顶部加"历史化"标注**（4.1/4.2/4.3 各加一行）：规范疑问查 SKILL.md，本页仅进度/教训。

### 2. 字段精确定义

- **`字段定义.md` compound `command_set`**：明确 = **本 CT 在 `## 配置方法` 步骤中编排的 atom 命令名**（= `组成` 边的 atom 命令名集合）；**不含**上游/前置依赖 atom（如 License `SET LICENSESWITCH`）、**不含**被本 CT 引用的其他 CT 的命令。复用判定（Jaccard）与快速查询均以此为准。

### 3. atom 范围澄清

- **`SKILL.md §A.2`**：atom 范围 = 所有命令都建（结构一致）；但 **FT/CT 配置流程只引用配置类命令 atom**（ADD/MOD/SET/DEL/RMV/LOD/持久化 STR）。查询/调测类（DSP/LST/EXP/STP/调测）atom 按命令层 md 梳理（无特性配置示例的第二批），但**不被 FT/CT 编排引用**（调测剥离）。即：atom 全建，但 FT/CT 引用面只覆盖配置类。

### 4. CT 抽取阈值入 SOP

- **`SKILL.md §B.4/§B.5`**：
  - **<3 distinct 配置 atom → 直引 atom，不抽 CT**（floor）。
  - **相位同义操作化定义**（复用判定门槛）：① 配置目标同（解决同一配置问题）② 对象链同义（操作的对象/前后序一致）③ 共享命令的相对顺序一致。三项满足 ≥2 项 = 相位同义。
  - Jaccard 是门槛，**配置语义判定优先**（语义不同则不复用，不论 Jaccard 多高）。

### 5. check.md 增信息可追溯性审查项（核心）

feature_task 审查项表新增 4 行（B1-B4）：

| 类别 | 检查点 |
|---|---|
| **B1 命令闭包** | Feature 簇任务脚本/数据规划的**配置类命令集合** ⊆ {FT 配置流程 atom 引用 ∪ 引用 CT 的 command_set 执行子集 ∪ 激活方法表省略列}。每条 Feature 配置命令须可由 FT/CT 还原或显式省略；静默丢失 = CRITICAL。 |
| **B2 参数闭包** | Feature 数据规划每条 `param=value` ⊆ {FT 激活方法差异相对基线列 ∪ 引用 CT 场景差异 ∪ 参数核对}，或显式标注"待数据规划补齐/冲突"。静默丢失 = CRITICAL；标注待补但 Feature 实有值 = MEDIUM。 |
| **B3 反向追溯** | FT/CT 中每个 `param=value` 须可追溯到 Feature 簇某行/某脚本；无 Feature 来源的参数（臆造变体行）= CRITICAL。 |
| **B4 信息源边界对账** | FT 若声明信息源边界（覆盖簇子集），须**逐文档枚举排除项 + 论证**（部署态/可选子功能/调测/纯原理/非本 NF）；不得静默排除承载配置命令的簇文档。静默排除 = CRITICAL（防 112001 类）。 |

### 6. audit 脚本扩展规格（交集成轨道实现）

`audit_compound_feature.py` 新增（python，集成 Agent 实现，本 CR 只出规格）：

- **D5 升级**：atom 覆盖率由 info 升为 **warning**（配置类命令引用 atom 不存在 = warning，提示 atom 轨补建；不阻塞集成）。
- **D6 命令闭包（新，CRITICAL 级）**：对每个 Feature，读其簇任务脚本/数据规划，抽配置类命令集合 CmdFeature；读 FT 配置流程 atom 引用 + 引用 CT command_set + 激活方法表省略列，得 CmdTask；**CmdFeature − CmdTask ≠ ∅ → CRITICAL**（列出丢失命令）。
- **D7 参数闭包（新，CRITICAL 级）**：对每个 Feature 数据规划 param=value，查是否落在 FT 激活方法差异/CT 场景差异/参数核对 或 标注待补/冲突；**未落且未标注 → CRITICAL**。
- 实现复用 `collect_command_examples.py` 的 ②-A 命中抽取（已能从 Feature 簇抽命令+参数）作为 CmdFeature/ParamFeature 来源；FT/CT 侧解析复用 audit_compound_feature 现有 yaml/边解析。
- **盲区独立性**：D6/D7 的 Feature 侧抽取正则须与 builder 用的不同源（沿用 CR-20260803-001 核查独立性原则）。

### 7. 审查独立性统一

- **`check.md` 审查角色纪律**明确：审查须由**独立 Agent**（非构建者本人、不改文件）；构建方**可自派子 Agent 做预审/自检**，但**不替代独立审查**（独立审查仍是合入共享 CT/集成的硬前置）。统一 SOP §B.7 与 handoff §5.9 的分歧。
