> 本文件不替代 `task/SKILL.md`。它把 SOP 的“逐 Feature pass”组织为可并行的领域批次，并明确共享步骤的写入边界。

## 1. 基本结论

- 构建单元仍是 **一个 Feature 的完整 pass**：同一 pass 中同时产出 `FeatureTask` 与 0～N 个 `CompoundTask`，不能把两类对象拆成不同流水线。
- 一个领域批次由 3～6 个同一对象链的 Feature 组成；常规批次控制在约 25～45 篇 Feature md。重型 Feature（约 12 篇以上）单独批或最多与 1～2 个紧密特性成批。
- 常规输入只包括：该批 Feature 文档簇、相关 AtomTask、CompoundTask `_index.md` 与现有 CompoundTask。原始产品文档仅在 Feature 资产不足时回查。
- 当前 SOP 的运行准入规则为：**本批 Feature 涉及的配置类命令必须已有 AtomTask 且其参数字典可核；缺失即阻塞该 Feature，不得在本批补造 AtomTask 或编造流程。**AtomTask 可以提前全量建设，但不阻塞无关领域的 Feature/CompoundTask 批次。

## 5. 集成与验收

构建 Agent 每批提交：FeatureTask、仅属于本批的新 CompoundTask、对既有 CT 的待回填清单、Atom 缺口清单，以及“激活方法—命令相位—AtomTask—参数差异—对象”的逐场景追溯表。该表中的差异必须同步落入对应 FeatureTask/CompoundTask 的正文，不能只存在于交付消息。

每个批次强制采用下列闭环；**未通过独立审查的批次不得进入全局索引**：

1. 构建 Agent 按《UDG特性与步骤Task构建提示词》完成 FeatureTask 与 CompoundTask，并先做自身准入/结构审计；
2. 审查 Agent（不得是构建 Agent，也不得改文件）使用该提示词内的“对抗评审提示词”，逐场景核 Feature 步骤、Atom 参数和 CT/FT 反链；
3. 任一 CRITICAL/HIGH 问题退回构建 Agent修正；涉及共享 CT 的修正列入待整合回填；
4. 审查 Agent 对修正范围复审。只有 CRITICAL/HIGH 均为 0，才由集成 Agent 合并共享 CT 场景差异、重生 `_index.md` 并运行 `audit_compound_feature.py`；
5. 集成 Agent 复核索引、反链与跨批冲突，并将审查结论附在批次交付中。

审查最低覆盖：每个 Feature 的每种激活方法/分支必须核验命令顺序、命令子集、执行对象、每个实际参数和值、`REFRESHSRV` 的次数与位置；每个 CT 必须核验其场景差异没有吞掉 Feature 的专属差异。
